Baseline: G-switcher 2.0.1 candidate `6aaa3146cf9b077f708c65d7cefe70d064badff5`.

The migration is intentionally behavior-neutral: if an OpenSpec baseline statement conflicts with reviewed 2.0.1 behavior, tests, the security model, or release evidence, that discrepancy is a **migration defect**. It is not authorization to change the 2.0.1 runtime.

## Source-of-truth transition

During adoption, the existing 2.0.1 documents and tests remain the authority for the frozen release candidate. After this baseline is reviewed, validated, and merged following resolution of the 2.0.1 release branch, `openspec/specs/` becomes the primary living behavioral specification for future changes. Historical/release-specific documents remain evidence snapshots and deeper security/release documentation rather than competing mutable specifications.

## Required migration review

Before OpenSpec adoption is considered complete:

1. All nine capability specs must pass strict OpenSpec validation.
2. `scripts/verify_openspec_baseline.py` must pass.
3. The branch must contain no runtime diff against baseline commit `6aaa3146cf9b077f708c65d7cefe70d064badff5` under `src/`, `tests/`, `Cargo.toml`, `Cargo.lock`, `build.rs`, or runtime `assets/`.
4. Existing Windows/release/security workflows must remain present and unweakened.
5. Any material mismatch found during review must be fixed in the OpenSpec migration unless a separately approved behavioral change explicitly changes the product contract.
