# Released original failure after a host reboot

This is an explicit recovery phase for an original quiescent FAILED managed invocation whose source lease has already been genuinely released. Ordinary `verify_terminal` still requires its original boot to be current. Missing, still-running, UNKNOWN, successful or unreleased invocations do not qualify. Historical bytes and wrapper exits cannot release a slot.

The deployed root operator uses `scripts/managed_boot_transition.py` with the exact original request, supervisor observation and genuine release receipt. The producer reads current procfs boot/PID namespace, machine identity and the last entry for that original boot directly from the local system journal. It accepts no caller-supplied host facts. No persistent same-machine journal, inconsistent chronology or different host remains blocked.

Write the one short-lived attestation exclusively to a regular root-owned file with a configured service reader group and root-owned non-writable ancestors. Symlinks, hard links, writable custody, oversized/duplicate records and replacement writes are refused. Do not copy it to a user-writable task directory. It expires after120seconds; a fresh observation is evidence preparation, never a native send or task replay.

The existing native closeout caller invokes `ManagedExecutorRuntime.verify_released_terminal_after_reboot` with the exact original task/attempt, real GitLeaseStore, release receipt and protected attestation path. The SDK checks the original request/claim, waitpid_ECHILD process set, genuinely issued v2 capability, historical canonical running pool, owned lease and actual release, then current physical PID absence. Only in this authenticated reboot route, a still-present descendant PID with a verified different numeric birth identifies a foreign process. The proof records its old/current births in `reused_descendant_pids`; `fresh_physical_absence` refers to original process identities, not all numeric PIDs being unused. The SDK never signals the foreign process. Same or unreadable birth, and any present original worker, supervisor or controller PID, remain denied. Original boot identities remain unchanged in every historical record. It returns the same sealed package-owned terminal proof with separate boot-reconciliation evidence. Every use rereads the protected original attestation and native chain; serialized copies stay ordinary data.

This route does not acquire/release a lease, cancel work, publish source, turn failure into success, refund charges, clear UNKNOWN external effects or launch a worker. Keep original task/attempt/handle/Source/role/provider, reservations, outcomes, spent budgets and history. Metadata closure still belongs to the existing native control CAS. A lost closure reply requires observing that original result.

Canonical Source publication, exact hosted release gates, independent mandatory reviews and installed-runtime adoption remain separate. Preparation of this candidate never grants SDK hot editing, boot spoofing, a new controller, takeover or automatic deployment.

## Adopt the released recovery runtime

A historical FAILED may still have `terminal_pending` metadata when the old runtime cannot verify across boots. The explicit optional `terminal_reconciliations` argument of `unknown_recovery.migrate_intake_registry_cas` accepts a mapping of exactly those pending originals to their live sealed reboot terminal proofs. This is used only in the existing qualified runtime-adoption maintenance protocol with the separately released new SDK. It does not activate the package or close any task.

Every pending row must be a genuinely failed/released v2 writer with no CI custody, no publication and the exact original Source/start digest/handle/attempt/plan/endpoint/release. The SDK rereads the original native session and revalidates the root boot proof again at native CAS validation. A serialized proof, foreign handle, extra active/UNKNOWN attempt or stale root record is rejected. The proposed document changes only `registry_digest`; all task states, original budgets/spent/UNKNOWN and queue bytes stay exact. The ordinary no-proof migration remains blocked by active rows.

After genuine released-runtime adoption, the existing native controller obtains a fresh short-lived root attestation and performs the original metadata closeout through its standard typed terminal gate. An unreleased candidate, read-only qualification or accepted registry migration alone never grants that closeout.
