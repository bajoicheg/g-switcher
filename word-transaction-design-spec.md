# Word transaction design: independent technical investigation

Inspected exact diagnostic candidate `3407a2d0570b88864fd265de61a8761999995380`, not current branch approximations. Product source release remains `10b7e90dfa9521170c48d9f09e2c5a4d6d77c3c3` per parent observation. No product changes, tests, remote mutations or launches performed. This report proposes an implementable direction, not a verified repair. CDC2.12.1 full process and paused schedulers remain applicable.

## Findings supported by code and logs

1. The adapter performs multiple visible writes, with independent failure points between them. `word_native.rs:517–658` reads the full document, checks initial selection, starts a custom Undo record, then loops character-by-character (`575–608`). Each changed character is a separate Range.Text property put. A later selection mismatch (`585–587`) returns without reverting already submitted changes. The code intentionally avoids automatic rollback of uncertain mutations. `UNCERTAIN_MUTATION` becomes true before StartCustomRecord (`562`) and clears only after full text/selection/Undo checks (`658`). It is a process-local global (`42`), so subsequent native reads and writes are refused (`220–230`). The trace character-write is an ATTEMPT marker; it precedes the put and is not independently a completion receipt.

2. Log(2), PID15628: writes attempted at1791549624537 and1791549624583, selection-moved at1791549624610, attempted Undo end, retained uncertain latch, repeated refusals. Log(3), PID11356: one earlier six-attempt correction completed; a later correction attempted three writes at1791558259883/9933/9978, selection-moved at1791558260012, retained latch. User-reported partial text plus this source path supports partial replacement; logs alone do not contain document text or prove every attempted put completed. The successful earlier correction rules out an adapter that universally refuses Word.

3. Main runtime serialization does not stop Word receiving ordinary keys. `windows_runtime_v201.rs:333–345` holds Engine mutex while executing corrections. The low-level keyboard hook is on its own thread and posts runtime events but forwards ordinary keys to Word (`448–493`); only recognized hotkeys are suppressed. Thus queued runtime work can remain undelivered while Word's caret/document continues changing. Mouse invalidation/generation changes can also happen. The logs do not distinguish incoming typing, Word's own range/selection adjustment, AutoCorrect, add-in or IME as the cause of selection drift. Relaxing the selection guard or removing evolving-range checks would conceal this uncertainty, not resolve it.

4. The native path still blocks the caller without a total bound. `word_native.rs:211–292` serializes via process-local mutex and spins/pumps sent messages until the operation STA completes, then joins. NativeOM acquisition, IDispatch Invoke, interface release and CoUninitialize can block. They have diagnostic stage observation, not safe cancellation. Runtime Engine remains held, so posted correction/key/GUI work stalls. Existing sent-only pumping intentionally avoids posted runtime reentry; restoring full main message dispatch while holding Engine is unsafe.

5. Fresh focus observations already use a windowless MTA (`word_focus.rs:27–77`) and a single read-only worker with750ms caller bound (`read_worker.rs:31–123`). Timeout returns None; that exact provider request keeps running until completion, no second call is admitted on the same worker, late reply is discarded. In log(2)/(3), fresh PID23548 successfully opened one native context then timed out in fresh-uia-focus at1791550203505. It had not reached native-window-acquire or mutation in that failed operation. This is separate from the earlier partial-write/latch failure. There are at least two UIA reader instances: Word focus and generic secure metadata; their independence does not guarantee Word's provider itself is healthy.

6. Restarting switcher clears its process-local latch/mutex/readers and can create new provider calls while Word still has earlier server-side work. The supplied logs do not identify the current minutes-long hang's exact external call or prove deadlock. Word/provider/add-in load, unfinished UIA, unresolved native call and host-side state are hypotheses. A restart is not authenticated quiescence or repair. Source also continues to request repeated fresh focus inside bound/stable and every character; a correction costs many cross-process UIA+NativeOM calls even when healthy.

## Assessment of candidate approaches

| Approach | Benefit | Limitation / decision |
| --- | --- | --- |
| Debounce and coalesce correction requests | Reduces stale immediate corrections during fast typing and concurrent queued work | Cannot make multiple puts atomic or serialize Word's UI/IME/add-ins. Useful admission step, insufficient primary repair. |
| Queue/suppress user keys during all COM work | Can narrow keyboard interference | Hook must remain fast; lossless replay on unknown outcome, layout/focus/IME and mouse/caret behavior is difficult. Cannot block provider indefinitely or call BlockInput/global flags. Avoid as the first implementation. |
| Replace entire range with one Text put | Eliminates application-level character loop | Plain text operation does not provide a per-character mixed-format contract. Do not use as the mixed-format repair. |
| Staged formatted range / OOXML payload, one destination commit | Eliminates application-level partial-prefix loop while retaining mapped character runs | Requires a strict supported-format subset, fresh precommit checks and real Word round-trip validation. Single COM call is not documented ACID or safe-cancelable. Unknown result still latches. |
| Separate persistent broker process | Stops COM waits from freezing switcher runtime and can retain target busy/uncertain state across switcher restart | Does not bound Word server execution, undo partial effects, or make killing helper a completion proof. Must forbid replacement writer while old call/outcome remains unknown. Recommended containment together with staged commit. |

## Minimal implementable design

A. Introduce explicit Word operation state before changing mutation semantics: Idle → Preparing → Committing → Verifying → Idle; any unresolved external boundary → Busy/Uncertain. One persistent broker owns native Word STA and windowless MTA readers; all COM interfaces and apartment cleanup stay there, only value messages cross IPC. One transaction slot, no autonomous native retry, no queued mutations. Main runtime submits/observes asynchronously, releases Engine before waiting, continues handling Chrome/UI/ordinary hook work. Use operation ID + process birth identity + document identity + focus/runtime generation; stale replies cannot grant mutation or clear newer state.

Broker admission must survive switcher restart. Use a single-instance authenticated local IPC endpoint and named ownership mechanism scoped to user/session and Word PID+creation time. Record operation state before first side effect, retain uncertain marker durably if helper/parent dies. The mutex alone is insufficient: abandoned mutex only proves client death, not Word-server completion. Reconnect to the existing broker; do not spawn another writer or security reader against a still-pending target. Unknown native mutation disables further Word access/mutation for the relevant Word process, including its other documents, until exact completion/reconciliation or that host process has truly exited. Do not automatically close/restart Word or discard unsaved work. Read-only provider timeout may bound UI immediately but admit another fresh provider request only after the exact old request actually completed; persistent broker keeps this fact across client restart.

B. Add a hook input sequence (incremented for every relevant ordinary key/mouse/invalidating event), distinct from the existing focus generation. A correction is considered only after a short bounded quiet period, no newer pending request, matching focus/process/sequence, and the user's actual suffix is freshly observed. Debounce delay is an implementation parameter requiring typing tests, not a promised timing constant. Coalesce/discard stale requests; do not retry a rejected correction just because a timer fired. Fresh security, protection, document/range and generation checks still gate commit. Broker must obtain a fresh operation-bound runtime-policy response (pause, policy epoch, input sequence and current generation) from the responsive parent before commit, or use authenticated shared counters with equivalent current semantics; a policy snapshot captured when the request was queued is insufficient. No stale positive permission or global Word application flag is introduced. This reduces collisions without pretending to lock Word input.

C. Replace the visible per-character loop with a staged, formatting-preserving *single destination operation*. The smallest promising no-clipboard/no-global-flag prototype is target Range.WordOpenXML → in-memory strictly validated fragment → modify only exact mapped text nodes → Range.InsertXML once. Preserve all original run/paragraph properties, styles and mapping byte-for-byte except intended text nodes; validate original flattened text and equal UTF16/BMP length exactly. Begin with small single-paragraph flat text runs, no paragraph marks, controls, fields, revisions, tables, drawings, bookmarks/complex markup or unsupported relationships; refuse unsupported content rather than silently normalize it. Current broad document structural guards stay. Parsing must disable external entities/resource fetches and enforce size/complexity limits. A transformed fragment is accepted only if every destination character maps to the original formatting run and all non-text metadata remains unchanged. Existing paragraph/capitalization matching applies to actual original; Undo records that original.

FormattedText is another documented single-destination option if an independently prepared Range with verified formatting can be obtained, but duplicating a live Range is not a detached copy. Preparing by writing to a duplicate still edits the user document. Creating/activating scratch Word documents changes application state and introduces more server calls; it is not the minimal safe implementation under the current no-global-flags/focus requirements. Do not assume a string can be assigned to FormattedText.

D. Immediately before the single destination commit, revalidate fresh security/focus/Word PID+birth/document identity/protection/generation/input sequence, target text and complete allowed-format fingerprint. Keep one custom Undo record. Set uncertainty before StartCustomRecord and the write. Postverify exact target/full relevant document and per-character formatting, selection/caret, fresh guards, successful Undo end. Only proven complete result clears uncertainty and emits correction context. A failed/hung call, end or postcheck never triggers blind Undo, fallback Text put, second writer or retry. Preserve existing fail-open behavior before any side effect. There remains a tiny external-input race between check and commit, and Word's provider can fail inside a single call; document this limit. This design eliminates our deliberate multiple-visible-write sequence, not every possible provider partial failure.

The conservative shipping rule is to keep automatic Word mutation disabled for unsupported/unverified formatted payloads until the real Word tests establish the contract. Do not claim guaranteed zero partial correction solely from debounce, broker isolation or InsertXML documentation. If a strict universal transaction guarantee is mandatory, the current external automation architecture cannot prove it; a Word-host component with controlled execution/transaction semantics would be a separate substantial design, not a shortcut.

## Meaningful verification before delivery

Portable: input burst invalidates/coalesces stale work; stale operation reply cannot clear uncertainty; no replacement broker/request after timeout; PID reuse differs by creation time; crash/restart reconnect retains pending/uncertain state; strict XML text mapping changes only intended nodes and refuses unsupported markup. Model before-side-effect refusal versus after-side-effect uncertainty.

Actual Word: identical mixed bold/italic/font/size/color/language/highlight/character-style boundaries before/after; spaces/punctuation and original case; exactly one Undo restores original text and formatting; rapid typing, mouse movement, IME and AutoCorrect; new input during preparation/commit; read-only/protected/tracked/structural documents refuse; injected COM failure/timeout before and after write; switcher restart while broker pending never issues another Word call; Chrome remains responsive. Compare the original failing per-character implementation against the new approach on the actual reproducible race. Full mandatory Windows CI and provenance remain required; they cannot replace installed Word acceptance.

## Primary documentation

Microsoft [UI Automation threading](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-threading) recommends non-window MTA for desktop client calls. Current Word focus reader follows that rule; threading guidance does not prove current server responsiveness.

Microsoft [Range.Text](https://learn.microsoft.com/en-us/office/vba/api/word.range.text) exposes unformatted text; [FormattedText](https://learn.microsoft.com/en-us/office/vba/api/word.range.formattedtext) uses a Range containing character formatting and includes paragraph formatting when a paragraph mark is present. [WordOpenXML](https://learn.microsoft.com/en-us/office/vba/api/word.range.wordopenxml) exports XML representing the range; [InsertXML](https://learn.microsoft.com/en-us/office/vba/api/word.range.insertxml) replaces range content from XML. These documents support the staged single-call prototype, but do not promise exact mixed-format round-trip fidelity, atomicity or cancellation; those remain acceptance requirements.
